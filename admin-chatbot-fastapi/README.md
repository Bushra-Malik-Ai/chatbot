# Directory — Admin Chatbot (FastAPI)

Admin chatbot that lets you add/remove/update users through natural-language
chat commands, with a "auto-login" that lets in anyone whose email already
exists in the directory.

## Project structure

```
admin-chatbot-fastapi/
├── app/
│   ├── main.py          # FastAPI app + routes
│   ├── database.py      # SQLAlchemy engine/session (SQLite)
│   ├── models.py        # User table definition
│   ├── schemas.py       # Pydantic request/response models
│   ├── nlu.py           # Rule-based command parser (the "chat brain")
│   └── static/
│       └── index.html   # Chat UI (vanilla JS, calls the API)
├── requirements.txt
└── README.md
```

## Run it in VSCode

1. **Open the folder** `admin-chatbot-fastapi` in VSCode.

2. **Create and activate a virtual environment** (VSCode will usually prompt
   you to do this — pick "Yes" — or do it manually in the integrated terminal):

   ```bash
   python -m venv .venv
   # macOS/Linux:
   source .venv/bin/activate
   # Windows:
   .venv\Scripts\activate
   ```

3. **Install dependencies:**

   ```bash
   pip install -r requirements.txt
   ```

4. **Run the server:**

   ```bash
   uvicorn app.main:app --reload
   ```

5. Open **http://127.0.0.1:8000** in your browser. Sign in with a seeded
   email (e.g. `samantha@company.com`) and try:

   - `can you add the user "john.smith@xyz.com" with phone number "+92332"`
   - `can you remove the user "john.smith@xyz.com"`
   - `can you update samanthas city to Cordoba`

   Interactive API docs (auto-generated by FastAPI) are at
   **http://127.0.0.1:8000/docs** — useful for testing `/api/chat` and
   `/api/users` directly without the UI.

A SQLite file `directory.db` is created automatically on first run, seeded
with three sample users. Delete that file to reset the data.

## How it works

- **Real authentication** (`POST /api/login`): a separate `admin_users`
  table holds bcrypt-hashed passwords. Login checks email + password and
  returns a JWT (`app/security.py`). Directory membership (`users` table)
  and chatbot access (`admin_users` table) are now **different
  permissions** — being listed as a person does not grant chatbot control.
  A default demo admin is seeded on first run:
  `admin@company.com` / `ChangeMe123!` — **change this password** (see
  below) before using this anywhere but your own machine.
- **Protected routes**: `/api/users`, `/api/chat`, and `/api/audit-log` all
  require `Authorization: Bearer <token>`. Missing or invalid token → 401.
  Enforced in `get_current_admin()` in `app/main.py`.
- **Audit log** (`GET /api/audit-log`, `AuditLog` table): every chat command
  is recorded with who sent it, what they typed, whether it succeeded, and
  the result — visible in the UI's third panel. This is the accountability
  trail any tool that mutates people data needs.
- **Chat command parsing** (`app/nlu.py`): a set of regex patterns that map
  natural sentences to one of three actions — `add`, `remove`, `update`.
  This is deliberately rule-based rather than an LLM call:
  - deterministic — same input always produces the same DB write
  - no external API cost, key, or latency
  - easy to unit test
- **Persistence**: SQLAlchemy + SQLite (`directory.db`). Swapping to
  Postgres/MySQL later only means changing `SQLALCHEMY_DATABASE_URL` in
  `app/database.py`.

## Changing the default admin password

The seeded password is only for first run. To change it:

```bash
python -c "from app.security import hash_password; print(hash_password('YourNewPassword'))"
```

Then update the hash directly in the database, or simplest for local dev:
delete `directory.db`, edit the password in `seed_if_empty()` in
`app/main.py`, and restart — it reseeds automatically.

## Setting a real secret key

`app/security.py` falls back to a hardcoded dev key if `CHATBOT_SECRET_KEY`
isn't set. Before deploying anywhere real:

```bash
# macOS/Linux
export CHATBOT_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"
# Windows (PowerShell)
$env:CHATBOT_SECRET_KEY = python -c "import secrets; print(secrets.token_hex(32))"
```

## Extending to LLM-based parsing (optional, more flexible)

Replace/extend `nlu.handle_command()` with a call to Claude using **tool
use / function calling**, defining tools like:

```json
{
  "name": "add_user",
  "input_schema": {"type": "object", "properties": {
     "email": {"type": "string"}, "phone": {"type": "string"}}}
}
```

Feed it the user's message, let the model pick a tool + arguments, then run
the same `models.User` DB operations already in `nlu.py`. Keep the regex
parser as a fallback/validator for when the LLM call fails or returns an
unrecognized field — cheap guardrail against a bad write.

## Still on the roadmap before real production use

This version fixes the two biggest gaps (real auth, audit trail). What's
still missing for a genuine production deployment:
- **Rate limiting** on `/api/chat` and `/api/login` (brute-force protection)
- **Token refresh / revocation** — current tokens are valid for 8 hours with
  no way to invalidate one early (e.g. on logout from another device)
- **Postgres** instead of SQLite for concurrent multi-user access
- **HTTPS termination** (via a reverse proxy like nginx or a platform's
  built-in TLS) — tokens sent over plain HTTP can be intercepted
- **Password reset flow** and admin user management (currently: edit the DB
  directly to add/remove admins)
